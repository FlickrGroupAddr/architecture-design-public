# ADR 0044: Use canonical grouped Crockford Base32 for Plugin Codes

Date: 2026-09-03

Status: Accepted

## Context

The private-MVP installation credential contains 256 bits generated by the FGA
API backend's runtime or operating-system cryptographically secure random
generator. The original design left its opaque text encoding and the visual
style of the one-time browser value and transient FGA LrC plug-in input open.

The first-publish storyboard review found that masking both surfaces prevents
the photographer from checking that the local paste matches the one-time value
before **Store and verify**. The accepted transfer ceremony already prohibits
observers, recording, clipboard history and synchronization, and durable
browser storage. Masking therefore adds transfer uncertainty without creating
the ceremony's confidentiality boundary.

RFC 4648 notes that no universally accepted base alphabet satisfies every
human-use requirement. Conventional base64url is compact but mixes case and
issues `0`, `O`, `1`, `I`, and `l`. Base56 variants exclude more ambiguous
characters, but their alphabets and leading-zero rules differ between
implementations. Crockford Base32 is an established human-oriented encoding,
is naturally aligned to five-bit groups, and emits uppercase symbols from the
fixed alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. It excludes `I`, `L`, `O`,
and `U`; the issued `0` and `1` therefore have no letter lookalikes in the
canonical alphabet.

Codex recommended canonical Crockford Base32 with strict FGA parsing instead of
an incompatible Base56 variant or a custom reduced alphabet. Terry approved
that recommendation on 2026-09-03. This is not an owner override.

## Decision

The FGA API backend generates exactly 32 random octets and encodes their
left-to-right bit string with the Crockford Base32 alphabet. It appends four
zero pad bits at the least-significant end to complete the final five-bit
symbol. The resulting 52 symbols are rendered and transmitted as thirteen
four-symbol groups separated by twelve ASCII hyphens:

```text
XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX
```

The 64-character grouped value is the complete canonical FGA installation
credential. The hyphens are part of the value hashed by the FGA API backend,
stored by the FGA LrC plug-in, and sent after the `Bearer ` prefix. The final
symbol is `0` or `G` because it contains one random bit followed by the four
required zero pad bits. No checksum is appended.

The FGA User UI and FGA LrC plug-in display the complete value simultaneously
in clear text before **Store and verify**. Both surfaces use the same
monospaced font, size, case, quartet grouping, and visually distinct zero. The
clear text remains transient: the browser still displays it once, and the FGA
LrC plug-in still clears its input and Lua references immediately after
`LrPasswords.store`.

The only accepted grammar is:

```regex
^[0-9A-HJKMNP-TV-Z]{4}(?:-[0-9A-HJKMNP-TV-Z]{4}){11}-[0-9A-HJKMNP-TV-Z]{3}[0G]$
```

The FGA LrC plug-in validates that exact 64-character ASCII spelling before
storage. The FGA API backend validates the same grammar before digest lookup.
Neither component trims whitespace, changes case, removes or relocates
hyphens, accepts Crockford aliases, ignores non-alphabet characters, repairs a
pad symbol, or decodes and re-encodes a presented credential. A mismatch is a
malformed or unknown bearer value, not an input-normalization opportunity.

The grouped value satisfies RFC 6750's `b64token` grammar. It remains an opaque
FGA bearer credential, not an OAuth token or a number clients may interpret.

## Consequences

- The photographer can compare the browser and plug-in values before creating
  durable endpoint state.
- The wire value still carries all 256 hosted-CSPRNG bits; grouping changes no
  entropy.
- One canonical spelling keeps SHA2-256 lookup, logging redaction, equality,
  and test fixtures straightforward.
- A copied value with altered case, whitespace, an alias, or different hyphens
  fails instead of being silently repaired. Recovery remains revocation and
  new issuance.
- The visible one-time value requires the transfer ceremony's existing
  no-observer and no-recording preconditions. Masking is no longer an allowed
  implementation variation during transfer.

## Alternatives considered

- **Keep 43-character base64url:** rejected because mixed case and the full
  alphanumeric alphabet make side-by-side human comparison unnecessarily
  error-prone.
- **Use Crockford's permissive decoder:** rejected because case folding,
  `I`/`L`/`O` aliases, and ignored hyphens create multiple spellings for one
  credential and conflict with strict digest lookup.
- **Choose a Base56 variant or custom reduced alphabet:** rejected because no
  single interoperable definition satisfies the requirement, and bespoke base
  conversion would add implementation and test surface without adding
  security.
- **Append Crockford's optional checksum:** rejected because the authoritative
  current-installation read already verifies the complete high-entropy bearer
  value, while the checksum adds symbols and parsing without preventing use of
  a stolen valid value.
